# Review, 2026-11-21

Initial look-over (analysis, a local build, next steps; no feature work, nothing pushed or deployed, Heroku untouched).
Branch `review-2026-11` holds the minimal port described under "Local build" plus this file.

## What it is

A multiplayer game clock (chess-clock style, any number of players), live at gmclk.com and gentlemans-clock.com
(2013-2015, Heroku). Time per turn plus time per game, count up or down.

- **Client** (`static/js`): Backbone + jQuery 1.10 + Bootstrap 2 + RequireJS, bundled by r.js into `main-built.js`.
  It is local-first: a private game lives in `localStorage` (`localGame`) and never touches the server. Only a game
  made "public" syncs, through a custom `Backbone.sync` that emits `create`/`read`/`update` over Socket.io.
- **Server** (`app.js`, 390 lines): Express serves `/` (an underscore template `views/index.html`, which injects the
  server clock for skew correction), `/js`, `/css`, `/static`, `/font`, and `/viewStats`. Socket.io handles the three
  game events and broadcasts `update` to the room. Mongoose stores one `Game` collection (join code of 5 lowercase
  letters, up to 12 players each).
- **Runtime needs:** MongoDB (`MONGOLAB_URI`, default `mongodb://localhost/gameclock`), `PORT` (default 3000), websockets
  or polling on the same origin. No other env vars or secrets. State is only the Game collection; a game is
  disposable.

## Review

Correctness
- A malformed message kills the server. `socket.on('read', ...)` does `req.model.join_code.toLowerCase()`; a client
  sending `{model:{}}` throws in the handler and, with no `uncaughtException` handler, the process exits (reproduced).
  Same in `update`. Any visitor can take the service down.
- `update` on an unknown join code silently creates a new game (`createGame(req)` with the *client's* fields), and
  `new Game(req.model)` / `game.set(gameData)` take any schema field the client sends (state, dates, arbitrary player
  arrays) with no validation beyond the schema.
- `createGame` never checks for a join-code collision (TODO in code); the unique index turns it into an error, which
  `create` now returns as a message string but the client treats as success-or-error only loosely.
- `players.guid` has `unique: true` across all games' subdocuments, so two games can never share a player guid and a
  client-picked duplicate rejects the whole save. The turn-time logic in `update` has large commented-out chunks and is
  marked "goofy" by its author; it needs tests before anyone changes it.

Security
- No secrets in the working tree or in history (checked all 55 commits: only `MONGOLAB_URI` read from the environment;
  the committed `views/.index.html.swp` is an editor swap file, no credentials). The real credentials lived in Heroku
  config; rotate/delete that MongoLab database when the Heroku app is retired.
- The join code is the only access control (5 letters, about 11.9 M values) and `/viewStats` lists every code with ages
  to anyone, so any visitor can open and edit any game. For a clock between friends this may be acceptable; if not,
  remove `/viewStats` (or put it behind a token) first.
- No rate limit, no origin check on websockets, no input length limits except the 12-character player name.
- Old front-end libraries (jQuery 1.10, Bootstrap 2, Backbone, bundled json3/date-shim) carry known XSS advisories;
  player names are user content shown in the page, so check how the templates escape them before relying on it.

Outdated
- Server side is now current. The client is entirely 2013-vintage and shipped as a prebuilt bundle.

## Rehosting plan (Sterling's setup)

Shape: a static client at `gentlemans-clock.sterlinghirsh.com` (Cloudflare Pages) and a realtime server at
`gentlemans-clock.rt.sterlinghirsh.com` on realtime-1 (Caddy site from deploy-kit's generic template, `deploy/game.conf`,
systemd unit; see projman `DEPLOYMENTS.md` "Adding a realtime service" and kitten's README "Deploy"). Do not start until
deploy-kit's host layer (branch `deploy-kit`) and the Cloudflare account are live.

1. **Decide the persistence.** Games are tiny and short-lived. Drop MongoDB: keep games in server memory (plus an
   optional JSON snapshot file) and expire them after a day idle. That removes the only external dependency and the
   MongoLab/Atlas bill. Everything else in `app.js` is small.
2. Make the socket URL configurable (`io(window.GC_SERVER || undefined)`) and add CORS for the Pages origin on the
   server (`cors: {origin: [...]}`), or serve the whole thing same-origin from realtime-1 as asteroid-blaster does.
3. Fix the crash and validation issues above (a shape check on every event, ignore bad input, no create-on-update).
4. Static build: copy `views/index.html` to a plain `index.html` (the only template use is the server clock; replace it
   with a `time` ack from the server), publish `static/` plus `main-built.js` to Pages.
5. Domains: `gmclk.com` / `gentlemans-clock.com` may still be Sterling's; point them at Pages as a redirect once it works.
6. Retire Heroku and MongoLab after the cutover (Sterling's step; not touched here).

## Rework under kitten: yes, worth it, but as a rewrite

The app is a good first small kitten game-or-app: simple state machine, tiny wire protocol, and a real need for a room
server with a server clock. Under kitten it becomes a Rust `kitten_net::Game` (room per join code, `on_message`
with a typed schema, snapshots only on change rather than 20 Hz) plus a small TypeScript/DOM client; the template's
deploy convention then gives the Pages + realtime-1 split for free, and the crash/validation class of bugs goes away by
construction. Honest caveats: kitten is a game loop framework (SoA/SIMD/WebGL), which is far more than a clock needs, so
the benefit is mostly the deploy path and the typed room server. If kitten's `--server` template isn't ready, the
cheaper route is steps 1-6 above on this Node code (a day's work), then port later. Recommendation: do the cheap route
first only if the old URL matters; otherwise start the rewrite from `kitten-new.mjs new gentlemans-clock --server`.
